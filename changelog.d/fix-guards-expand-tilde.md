- **`public-text-guard` and `instance-key-gate` expand `~` in a command's paths, as the shell does.** (test: T1) Measured 2026-10-18 on the Windows instance: `git -C ~/Projects/<private clone> commit -m "<name>"` was refused as "a repo whose visibility is unknown" — the guard resolved the literal `~`, found no remote and treated the private shared-memory clone as public. The same gap had a leak side: a `--body-file ~/<file>` stayed unreadable for the guard, so a watch-list name inside it was never scanned and the post went through; and `instance-key-gate` read no key from such a file and blocked a post that carried one. Class search over `helpers/`: five sites resolve a path from the command text without expansion — four in `public-text-guard` (target repo, located paths, handed-over files, author dir) and one in `instance-key-gate`; every other helper that takes a `~` already expands it on its own. Both now expand `~` and `$HOME` first. Fixtures: `git -C ~/<private clone>` passes, `~/<public clone>` blocks, a name inside `--body-file ~/<file>` blocks, a clean one passes, a key inside `--body-file ~/<file>` is read. Negative control measured: with the previous helpers exactly those cases fail (public: 2 of 4, key gate: 1 of 1).
