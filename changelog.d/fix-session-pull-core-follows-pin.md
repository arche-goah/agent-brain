- **`session-pull.sh` keeps `core/` on the brain's pin — forward only, by state, at every start.** (test: T2) Measured 2026-10-22 on a machine a week behind: the start pull brought the brain up to date, `core/` stayed on the old release, and the new hooks in `.claude/settings.json` called core files the old checkout did not have — every tool call was refused from then on, the session could not repair itself, and the operator had to run commands by hand. The pin is what `brain-update.sh` already committed on another machine, so following it is no plain pull of the submodule. Before and after the brain pull, a `core/` that lags the brain's own pin is checked out on it — only a clean detached checkout that sits on a commit an earlier brain commit pinned, only forward, never a declared alpha; a pin that moved BACKWARDS is named with the rollback command and never checked out (the downgrade `brain-update.sh` refuses too), a branch or local edits stay untouched and are named. Because it goes by state, a move that failed once (or a machine stuck before this existed) heals at the next start, and while `core/` lags, the brain refusal names `core/` instead of "uncommitted changes". On Windows a file another process holds open is not replaced while git still exits 0 (measured: a Python or Node handle on a core file — "unable to unlink", rc 0; a running bash script is replaced fine), so the move is verified against `git status` and retried, else named. Plugins are not touched (the start report still says when they lag the pin). Fixture `scripts/test-session-pull.sh`: a pull that moves the pin moves `core/` and leaves the brain clean; `core/` on a branch is named; a backwards pin is not checked out; a failed move is named, refuses the brain with the real cause and heals once the obstacle is gone; a declared alpha is left alone — the new cases fail against the hook before this change (checked: 7 red).
