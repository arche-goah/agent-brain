- **`brain-update.sh` moves `core/` only on a fresh pin, and never backwards.** (test: T2) Measured 2026-10-22 on a Windows brain: `claude plugin marketplace update` failed ("not refreshed — continuing with cached state"), the cached core plugin still said 1.4.1 while the brain sat on v2.0.3, and the run checked out v1.4.1, committed the pin and pushed it — every other machine of that brain pulled the downgrade until it was reverted by hand. A pin read from a cache this run could not refresh is not the released state: when the core's OWN channel was not refreshed (its marketplace, or the core plugin's `claude plugin update` returning non-zero), `core/` stays, neither the core origin nor `.gitmodules` is re-pointed (both are committed and pushed below, so a cached entry naming an old repo would send every clone there), and the FAIL line names what was not refreshed; a failed UNRELATED marketplace no longer blocks the core. Independent of where the tag came from, a target that is an ancestor of the core the brain committed is refused with the explicit rollback command — a downgrade is never automatic. Fixture `scripts/brain-update-test.sh`: the real script against fake brains (core/ committed as a submodule, a `claude` stub per case, GitHub URLs redirected to a local origin): every refresh failing, a stale entry naming another repo (nothing re-pointed, nothing committed), a refreshed marketplace with a failed plugin update, a fresh run whose target is older than the committed core, and an unrelated failing marketplace next to a refreshed core one (core moves) — each fails against the script before this change (checked).
