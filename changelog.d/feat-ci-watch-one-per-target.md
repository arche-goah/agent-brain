- **ci-watch: one watch per target on a machine — a second call attaches to the running one.** (test: T1) (level: writer; higher: design — a machine-wide watch service that every session subscribes to; one lock directory per target does the same with no daemon; debt: the owner's stderr (an UNKNOWN verdict) reaches its own caller at the end, after stdout — every verdict is a final line anyway, and the lock does not span machines: two machines on one account still poll twice) Measured 2026-10-19 on the macOS brain: four sessions, a collab-watch and up to ~15 `ci-watch.sh` from sessions and agents polled one account at once; GitHub's secondary rate limit answered "API rate limit already exceeded" while the primary budget showed thousands free; three duplicate watchers on main were ended by hand. #35 made a watch wait a block out; this keeps the block from coming. A call with the same mode, repo, target and `CI_WATCH_SHA` as a running watch now prints one `CI-WATCH SHARED` line, reads the owner's result file (never GitHub) and ends with the owner's lines and exit code; a dead owner's leftover directory is taken over. The lock lives under `$HOME/.cache/ci-watch` (a session's `TMPDIR` can be private to it; `CI_WATCH_LOCK_DIR` overrides, `CI_WATCH_SHARE=0` turns it off).
