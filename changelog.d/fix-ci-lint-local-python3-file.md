- **`ci-lint-local.sh` puts a `python3` FILE first on PATH instead of a bash function, so a program that is not bash reaches the working interpreter too.** (test: T1) Measured 2026-10-25 on the Windows instance, where `python3` is the Store stub (OS-17): `ci-lint-local.sh lint` read the fixture-suite step red ("Python was not found; run without arguments to install from the Microsoft Store", 77 FAIL lines in `test-autonomy-diagnose.sh`) while the same fixture run directly is green and CI is green. Cause, read and reproduced: the tool exported `python3` as a bash function; the fixture's probe `command -v python3` returned the function's name, the probe call went through the function and passed, so the fixture kept `PY=python3` — and then ran `env -u … "$PY" …`. `env` is a separate program, knows no bash functions, and started the stub from PATH. Now the tool writes `<tmp>/py3/python3` (`exec` onto the probed interpreter) and BASH_ENV prepends that dir to PATH: bash, nested bash and every program a step starts find the same file. Fixture `scripts/test-ci-lint-local.sh`: new step `env python3 …` under the planted stub — passes, and fails against the function version (2 checks). With the stub step green, the suite reached `test-ci-lint-local.sh` itself for the first time under the tool, and its stub control failed there: the nested run inherited the outer run's BASH_ENV, which put a working `python3` first (with the old function the same). The control now runs with `BASH_ENV=` cleared. Real run on the stub machine: see the PR. (level: writer; higher: design — not needed: the tool is the one place that maps the runner's `python3`, and a file on PATH is what the runner itself has; debt: a native Windows program that starts `python3` itself (not through a shell) does not run a shebang file — no such caller in the CI steps today)
