- **The open-requests list no longer reports answered requests as open, and no longer hides requests addressed to us.** (test: T1) Measured 2026-10-19 on the macOS instance: 9 of 23 listed requests had been answered and still came back at every session start (some for four sessions), and 3 requests addressed to the instance were never listed. Three causes, one class (a reply is matched to its request by wording): (1) a colon inside parentheses in a heading (`AN x (status: open): …`, `AN y (one-machine: …), x: …`) ended the addressee list, so the title began with `open): …` and no reply could name it, or the second addressee vanished; (2) an answer that names the request in its own words (`re push route agreed` for `re push route — agreed`) matched nothing — the third phrasing patch after `re <what>` and the number rule, so this one closes the class: a `re <x>` names a request when every matter word of x stands in the request's title (at least two words, no number the request does not carry); (3) a file request was answered only by naming its file stem, while answers named the LOG heading that announced the file — the same reply rule now applies to both forms (the announcing heading must carry the path; a nudge that only mentions the stem is not a title). Fixtures: LOGONLY-PAREN, LOGONLY-WORDS, ANNOUNCED-ONE close; LOGONLY-WORDNUM (same words, other number) and LOGONLY-CC stay listed. Negative control measured: the previous reader keeps all three open and hides CC.
